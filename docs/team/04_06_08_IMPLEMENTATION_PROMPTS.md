## 6. 스캔 PDF OCR — 01

```text
목표: 스캔 페이지가 있는 PDF를 거부하지 않고 텍스트로 읽어 기존 추출 흐름에 넘긴다.
텍스트 PDF·TXT·XLSX의 기존 출력은 바뀌지 않아야 한다.

착수 입력 (사용자가 채움):
- 대표 스캔 자료 위치와 개수: ____
- 언어(한글/영문), 인쇄체/필기, 표 포함 여부: ____
- 같은 페이지 안의 텍스트·이미지 혼합(예: 머리말은 텍스트, 사양표는 이미지) 지원 여부: [지원] / [제외] / 미정

- OCR 출처 값 정책: [경고만 표시] / [사람이 수정·확정하기 전 승인 불가(can_register=false)] / 미정
- 실제 모델 실행 승인 범위(파일 수·호출 수·시간): ____

읽을 것: docs/team/01_PARSER.md, src/ontoproduct/services/parser_service.py,

현재 코드의 제약(구현 전에 확인하고 계획에 반영):
- read_pdf는 텍스트가 없는 페이지를 오류 없이 건너뛴다. 모든 페이지가 비었을 때만
  "스캔 PDF OCR 미지원"으로 거부한다. 따라서 지금도 혼합 PDF의 스캔 페이지는 조용히 빠진다.
- read_pdf의 ParsedPage (페이지 번호, 텍스트) 튜플은 Parser 내부 형식이다. state와 checkpoint에 저장되는 것은
  ParserService.parse가 만드는 ParsedDocument(source_file, text, page)이다.
  OCR 출처를 남기려면 ParsedDocument에 필드를 추가해야 하며(기존 checkpoint 호환을 위해 기본값 필요),
  내부 튜플도 그 값을 넘기도록 바꿔야 한다.
- OpenAiLlmService.generate_structured는 텍스트 입력만 보낸다. [A]는 이미지 입력 메서드 추가가 반드시 필요하다.
  또 LLM 서비스는 settings.LLM_AGENTS = ("extraction", "ontology")에 대해서만 만들어지므로
  OCR 항목 추가가 필요하다. 이 항목은 기본 모델(models.default)을 물려받게 하고, 추가 전에 확인받는다.
  요청당 timeout_seconds(현재 250초)·max_retries와 착수 입력의 허용 처리 시간을 함께 검토한다.
- 모든 작업은 이미 사람 검토 interrupt를 거친다. "사람 확인"은 표시·승인 가능 여부 정책으로 다룬다.

작업:
1. 위 제약을 확인하고, ParsedDocument 필드 추가와 (A이면) LLM 인터페이스·LLM_AGENTS 확장의
   변경 전후 형태·소비자·기존 checkpoint 복원 영향을 먼저 제시한다.
2. 빈 페이지와 스캔 페이지를 구분하는 기준(예: pdfplumber page.images 존재)을 정한다.
   텍스트가 없는 스캔 페이지는 OCR 경로로 보낸다(페이지 단위 혼합 PDF 지원).
   같은 페이지 혼합이 [지원]이면, 텍스트가 있는 페이지에서도 OCR할 이미지를 고르는 기준(예: 페이지 대비 이미지 면적 비율)과
   처리 방식(이미지 영역만 잘라 OCR 또는 페이지 전체 OCR)을 정한다. 로고 같은 작은 이미지까지 OCR하지 않게 한다.
   OCR 텍스트는 기존 텍스트와 구분해 같은 페이지에 붙이고, 같은 내용이 중복되지 않게 한다.
   [제외]이면 텍스트가 있는 페이지는 기존 방식 그대로 두고, 이 제한을 01_PARSER.md 지원 범위에 명시한다.
3. 페이지 이미지는 이미 설치된 pypdfium2(또는 pdfplumber)로 만든다.
   [A]이면 기존 OpenAI 클라이언트·모델 설정을 재사용해 이미지 입력을 추가한다.
   [B]이면 패키지·라이선스를 제시하고 확인받은 뒤 추가한다.
4. 근거 정책을 먼저 정하고 문서화한다.
   OCR 결과 텍스트를 해당 페이지의 원문으로 취급하고, 근거 인용은 그 OCR 텍스트와 대조한다.
   이 대조는 OCR 텍스트와의 일치만 보장하고 원본 이미지와의 일치는 보장하지 않는다는 한계를 적는다.
   OCR 출처 값은 검토 화면에 표시하고, 착수 입력의 "OCR 출처 값 정책"대로 승인 가능 여부를 정한다.
5. OCR 실패·빈 결과·시간 초과는 성공으로 숨기지 않고 기존 오류 경로로 보낸다.

먼저 작성할 테스트(통신은 고정 응답 또는 가짜 OCR 함수로 대체):
- 현재 동작 재현: 텍스트 페이지 + 스캔 페이지 PDF에서 스캔 페이지가 조용히 빠지는 것을 FAIL로 확인.
- 기존 텍스트 PDF 출력 불변(기존 test_real_parser.py 통과). 이미지 없는 빈 페이지는 지금처럼 건너뜀.
- 전체 스캔 PDF: 페이지 번호·source_file 유지, OCR 출처 표시.
- 혼합 PDF: 텍스트 페이지는 기존 텍스트, 스캔 페이지만 OCR, 페이지 순서 유지.
- 로고 같은 작은 이미지가 있는 텍스트 페이지: OCR 호출 0회, 기존 출력 불변.
- 같은 페이지 혼합이 [지원]이면: 텍스트 + 사양표 이미지 페이지에서 이미지 속 사양이 OCR 텍스트로 함께 나옴(먼저 FAIL 재현).
- OCR 실패/빈 결과/시간 초과는 오류로 보고되고 등록되지 않음.
- OCR 텍스트에 없는 인용은 근거 대조에서 거부됨.
- OCR 출처 값이 검토 화면 데이터에 표시되고, 선택한 정책대로 APPROVE 노출 여부가 정해짐.
- OCR 출처 필드가 없는 이전 ParsedDocument가 담긴 checkpoint 복원.

실제 확인(승인 범위 안에서만): 대표 스캔 자료로 업로드 → 추출 → 검증까지 실행하고,
파일별 성공/실패, 필수 추출 항목별 정답 대비 값·단위 일치 수와 분모, 처리 시간을 별도 보고서에 남긴다.

완료 기준(두 단계를 구분해 보고한다):
- 구현 검증 완료: 위 테스트와 전체 pytest 통과.
- 품질 수용 확인: 품질 수용 기준이 정해져 있고, 승인 범위 안의 실제 자료 결과가 그 기준을 충족함.
품질 기준이 미정이거나, 실제 실행이 미승인·미실시이거나, 기준에 미달하면
"구현 검증 완료, 품질 수용 미확인"으로 보고하고 그 사유를 적는다. 이 상태를 OCR 완료라고 보고하지 않는다.
```

## 7. 대규모 중복 조회 — 05·08

```text
목표: 같은 분류 제품이 많아져도 중복 조회 시간을 착수 입력의 목표 p95 안으로 유지한다.
판정 결과(verdict·score·top_k·동률 product_id 순서·근거)는 지금과 같아야 한다.

착수 입력 (사용자가 채움):
- 착수 근거: 한 분류 제품 수 ____개 / 측정된 단일 조회 ____초 (기준: 3,000개 초과 또는 1초 초과)
- 목표 규모(분류별 최대 제품 수)와 허용 응답 시간(p95): ____
- 동시 조회 수: ____ (기본값 1. 비우면 1로 측정하고 그렇게 보고)
- 대표 조회 분포(실제 제품 표본 위치 또는 사양 분포 설명): ____
  (기본값: 기존 예비 측정의 합성 최악 사례, 즉 모든 제품의 사양이 같은 경우. 비우면 이것으로 측정하고 그렇게 보고)

현재 판정의 특성(후보를 줄이거나 캐시할 때 반드시 지킬 것):
- judge에서 후보가 되는 조건은 "제품명 정규화 키가 같다" 또는 "핵심 사양 중 CONFLICT가 하나도 없다"이다.
  제품명이 같으면 핵심 사양이 충돌해도 POSSIBLE_DUPLICATE가 된다.
- CONFLICT가 아닌 경우: 값이 비어 있음(MISSING), 정규화 후 단위가 달라 비교 불가(MISSING),
  수치가 NEAR 허용 범위 안, 텍스트가 같거나 한쪽이 다른 쪽을 포함(NEAR), 그 밖의 값이 정확히 같음.
- 분류 매핑이 없으면 조회 제품의 모든 속성이 핵심 사양이 된다.
- 단위 정규화는 조회 시 Python에서 하며, 조회 제품의 매핑(properties)에 따라 후보 제품의 정규화 결과가 달라진다.
  매핑과 무관한 것은 structure()(product_json → NormalizedProduct) 결과까지다.
- 저장된 제품은 INSERT만 있고 갱신되지 않는다.
따라서 저장된 값의 일치 여부로 SQL에서 거르거나, product_id만으로 정규화 결과를 캐시하면 결과가 바뀐다.

읽을 것: docs/team/05_DUPLICATE.md, services/duplicate_service.py,
repositories/product_repository.py(실제 경로 확인), tests/test_real_duplicate_agent.py,
eval/duplicate_scale_probe.json, 04_REQUIREMENTS_06_08.md §7.

작업:
1. 예비 측정 재현(기존 결과 비교용): 예비 측정 스크립트는 저장소에 없고 결과(eval/duplicate_scale_probe.json)만 있다.
   그 조건(격리 합성 DB, 같은 Bearing 사양, 크기 100/1,000/5,000별 단일 조회 3회, tracemalloc 켠 상태)을 따르는
   스크립트를 scripts/에 만들어 남긴다. 최소/최대만 기록하고 p95는 계산하지 않는다.
   예비 측정의 시간이 tracemalloc을 켠 상태로 잰 값이라는 점을 기록한다. 기존 결과와 차이가 크면 원인을 보고한다.
2. 목표 검증 측정(1과 별도 실행, 같은 스크립트의 다른 모드로 남긴다):
   - 시간은 tracemalloc을 끄고 재며, 메모리(tracemalloc peak 또는 프로세스 RSS)는 별도 실행으로 잰다.
   - 목표 규모 DB에서 착수 입력의 대표 조회 분포로 조회 제품을 고르고,
     p95를 낼 수 있을 만큼 반복한다(반복 횟수와 그 이유를 기록).
   - 동시 조회 수가 2 이상이면 동시 실행 방식(스레드/프로세스, 연결 공유 여부)을 정해 기록한다.
   - 첫 조회(새 runtime·빈 캐시)와 반복 조회를 구분해 각각 최소/중앙값/p95/최대를 기록한다.
   - 측정 환경(OS·Python·CPU)을 기록한다. 이 측정을 변경 전 기준선과 변경 후에 같은 방식으로 실행한다.
3. 프로파일링으로 병목(SQLite 읽기, JSON 파싱, Python 비교)을 확인한 뒤 고친다.
   추측으로 고치지 않는다.
4. 먼저 결과를 바꾸지 않는 안을 적용한다.
   예: product_id별 structure() 결과 캐시(제품이 갱신되지 않으므로 무효화 대신 새 product_id만 추가로 읽음).
   정규화 결과까지 캐시하려면 키에 조회 제품의 매핑(properties)을 포함한다.
5. 그래도 목표를 못 맞추면 후보 제한을 검토한다. 후보 집합은 위 judge 조건을 만족할 수 있는 모든 제품,
   즉 "제품명 정규화 키가 같은 제품" 또는 "어떤 핵심 사양도 CONFLICT가 아닌 제품"을 반드시 포함해야 한다.
   이 조건을 SQL로 표현하려면 정규화된 값을 별도 열로 저장해야 할 수 있다. 그 경우 공통 규칙대로 먼저 제시한다.
   임베딩·벡터 DB·새 검색 엔진은 이 안으로도 목표를 못 맞출 때만 근거와 함께 제안한다.
   후보를 줄이면 전체 비교와 결과가 같은지 확인한다. 결과가 달라지는 사례가 있으면 보고하고 채택하지 않는다.
6. DB 스키마/인덱스 변경은 기존 사용자 DB에서 자동 적용되는지(마이그레이션)와 롤백을 문서화한다.

먼저 작성할 테스트:
- 변경 전후 같은 입력에서 verdict·score·top_k·순서·근거가 동일(여러 분류·동률 포함).
- 제품명은 같고 핵심 사양이 충돌하는 제품이 POSSIBLE_DUPLICATE로 계속 나옴.
- NEAR 허용 범위 안의 수치, 다른 단위로 저장된 같은 값(예: 0.6 kW와 600 W)이 기존과 같은 결과.
- 핵심 사양 일부가 비어 있는 제품, 정규화할 수 없는 단위의 제품, 텍스트 사양이 부분 포함인 제품도 기존과 같은 결과.
- 분류 매핑 없이(mapping=None) 조회해도 기존과 같은 결과.
- 캐시를 쓰면 새로 저장된 제품이 다음 조회에 바로 반영되고,
  같은 후보를 매핑이 다른 두 조회 제품으로 연달아 조회해도 각각 기존과 같은 결과.
- 실제 DB ID 검증 유지, 다른 분류 제품은 후보에 섞이지 않음.
- 기존 DB 파일을 열어도 동작(인덱스 생성이 있으면 멱등).
- 성능 테스트는 기본 회귀를 느리게 하지 않게 작은 규모로 넣고, 목표 규모 측정은 별도 스크립트 결과로 남긴다.

완료 기준: 목표 검증 측정(작업 2)의 p95가 목표 안이고, 결과 동일성 테스트와 전체 pytest 통과.
첫 조회와 반복 조회의 p95를 모두 보고한다. 반복 조회만 목표 안이면 목표 충족이라고 하지 않고 첫 조회 결과를 함께 적는다.
현재 구현으로 이미 목표 안이면 코드 변경 없이 측정 스크립트와 결과만 남기고 종료한다.
```

기준 데이터는 계속 SQLite product_json이다. 전용 RDF 저장소는 만들지 않는다.
