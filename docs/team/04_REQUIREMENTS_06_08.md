# 6~8 요구 확인 기록

기준일: 2026-10-09. 질문 목록을 만들어 사용자에게 확인받는 작업이다. 아래는 확인된 코드·설치·예비 측정이고, 아직 미정인 운영 목표를 확정한 명세가 아니다.

## 6. 스캔 PDF OCR

현재 Parser는 TXT/CP949/BOM, 텍스트 PDF·표·페이지, XLSX 시트/행/셀을 지원한다. 스캔 PDF는 `스캔 PDF OCR 미지원`으로 거부하며 `test_real_parser.py`에 회귀가 있다. inputdata의 PDF 10개는 텍스트 2페이지 문서다. 합성 scanned fixture는 있어도 대표 업무 스캔 자료는 제공되지 않았다.

PATH 조회에서 tesseract·ocrmypdf·pdftoppm을 발견하지 못했고 `.venv`에는 pytesseract/ocrmypdf/rapidocr/paddleocr가 없다. pdfplumber/openpyxl/Pillow는 있다. 설치 위치 전체를 검색한 결과는 아니다. 새 의존성 설치나 외부 자료 전송은 하지 않았다.

확인할 질문:

- 스캔 PDF 또는 텍스트/스캔 혼합 PDF 인식이 실제로 필요한가?
- 한글/영문, 인쇄체/필기, 표와 사양의 배치, 해상도·보통/최대 페이지 수는 무엇인가?
- 페이지당/파일당 허용 시간과 필요한 값·단위 인식 품질 기준은 무엇인가?
- 업무 자료가 외부 OCR 서비스로 전송되어도 되는가? 로컬 처리만 허용되는가?

요구가 확정되면 기존 텍스트 페이지를 유지하고 스캔 페이지만 처리하는 최소 경로부터 검토한다. page/source_file/evidence 유지, OCR 실패·낮은 품질을 성공으로 숨기지 않기, 혼합 PDF의 위치 보존이 수용 조건 후보다. 정확도 수치와 도구/라이선스 선택은 대표 자료와 허용 범위가 확인된 뒤 정한다.

## 7. 중복 조회 규모

현재 `DuplicateService.retrieve`는 같은 분류 전체를 Repository에서 읽어 Python으로 비교한다. top_k=3, 동률 product_id 정렬, 실제 DB ID 검증과 충돌 근거는 그대로 유지했다. 검색 방식·후보 제한·임베딩은 추가하지 않았다.

Windows 11 / Python 3.12.10, 격리 합성 Bearing DB에서 같은 내경/외경을 가진 제품을 생성했다. 크기별 단일 query 3회에 tracemalloc을 켜 Python 할당 peak를 측정했다. 원본은 [측정 JSON](../../eval/duplicate_scale_probe.json)에 있다.

| 같은 분류 제품 수 | 조회 시간 범위 | Python 할당 peak 최대 |
| ---: | ---: | ---: |
| 100 | 0.037~0.040초 | 약 0.27 MiB |
| 1,000 | 0.277~0.288초 | 약 2.74 MiB |
| 5,000 | 1.482~1.683초 | 약 13.50 MiB |

이것은 합성 예비 조사다. 프로세스 RSS, 동시 요청, 실제 제품 분포, tail latency, 운영 데이터 정확도를 측정하지 않았다. 위 수치를 목표 SLA로 채택하지 않는다.

확인할 질문:

- 전체 및 분류별 현재/목표 제품 수와 증가 속도는?
- 동시에 몇 건 조회하고 허용 p95 응답 시간·프로세스 메모리는?
- 대표 제품 분포와 중복 정답이 있어 후보 제한의 누락을 검증할 수 있는가?

답변 후 목표를 충족하면 추가 구현하지 않는다. 필요하면 SQLite 인덱스와 조회 계획, 필요한 후보만 읽는 방식을 먼저 비교한다. 후보를 줄이면 기존 판정·근거·top_k·동률 순서를 보존하며 정답 누락과 Precision/Recall 변화를 함께 측정한다.

## 8. RDF 저장

현재 제품의 기준 데이터는 SQLite product_json이며 `OntologyService.to_rdf`가 필요할 때 RDF를 생성한다. 제품별 시각화·SHACL·triple 표·Turtle/JSON 다운로드는 이미 제공한다. 지속 RDF DB나 제품 간 SPARQL endpoint는 없다. 기존 방식으로 충족되는 경우 새 저장소가 필요하지 않다.

확인할 질문:

- 제품별 그래프/다운로드가 목적이거나 여러 제품을 묶어 지속적으로 질의해야 하는가?
- 제품/관계 수, 조회 유형·빈도, 갱신·삭제 반영 시간은?
- 저장소를 운영할 환경, 외부 저장 허용, 유지보수·비용 제약은?

지속 저장을 선택하면 JSON 기준성, product/case ID, RDF 생성 버전, 갱신·삭제·재생성·이관을 정한다. SQLite 성공/RDF 실패와 반대 순서의 복구, 중복 갱신 멱등성, 기존 데이터 재생성 검증을 함께 설계한다. 사용자 DB 이관이나 외부 저장소 전송은 아직 하지 않았다.
